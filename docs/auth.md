# Вход: форма, каталог AD/LDAP, локальные пользователи, роли

Вход держит сам BFF (`app/auth/`, ручки `app/api/auth.py`, middleware `gate` в `create_app()`),
а не обратный прокси. Выключен (`auth.enabled: false`, умолчание) — сайт анонимный, правка
держится рубежами `editing`. Включён — всё, кроме формы и статики, требует сессии: API без
сессии отвечает `401 {"detail": "нужен вход"}`, страница уводит на `/signin?next=…`.

⚠️ **Почему форма, а не Basic Auth.** Прокси-помощники в браузерах (расширения для
корпоративного прокси) отвечают на ЛЮБОЙ 401-челлендж паролем от прокси и уводят вход в
цикл `ERR_TOO_MANY_RETRIES`, а человек не видит даже диалога. Поэтому `WWW-Authenticate` не
отдаётся никогда (закреплено тестом). И только так сайт знает, КТО правит.

⚠️ `/signin`, а не `/login`: на общем с чужим сайтом домене `/login` часто занят (у WordPress —
ядром, редирект на `wp-login.php`), а проксировать его к себе значило бы отобрать у соседа.

## Конфиг (`app/config.yml`, блок `auth`)

```yaml
auth:
  enabled: true
  session_days: 14                 # cookie, скользящее продление
  cookie_secure: null              # null — по факту (https или X-Forwarded-Proto за доверенным прокси)
  data_dir: ./data/auth            # ключ подписи и снимки учёток; путь — от этого файла
  ldap:
    url: ldaps://dc.example.org:636
    base_dn: dc=example,dc=org
    bind_template: "{login}@example.org"     # или "EXAMPLE\\{login}"
    ca_file: /etc/ssl/corp-root.pem          # корень домена, если системного доверия нет
    attributes: [displayName, givenName, sn, mail, title, department, memberOf, thumbnailPhoto]
    keep_raw_entry: false          # разовый взгляд «что есть по учётке» — включить на один вход
  users:                           # локальные: демо, гость, разработка без каталога
    - {login: kuznetsova, name: "Мария Кузнецова", password: "scrypt$…", role: admin}
  roles:
    default: editor
    by_group: {"CN=site-admins,OU=groups,DC=example,DC=org": admin}   # DN или CN, без регистра
    by_user: {kuznetsova: admin}
  access:
    groups: ["*_site-users"]       # маски групп: без них доменному пользователю сайт закрыт
    users: ["kuznetsova"]          # поимённо, поверх масок: кому сайт открыт и без группы
    message: "нет доступа к сайту"
  login_limit: {attempts: 4, window_seconds: 900, per_ip_attempts: 30}
```

Хэш пароля локального пользователя печатает `python3 tools/auth_password.py <логин>` (getpass).
Ключ подписи cookie генерируется сам в `data_dir/secret` (0600); задать — `auth.secret`.

## Каталог: своей учёткой, без сервисной

`bind_template` превращает логин в имя для bind'а (AD принимает `login@domain` и
`DOMAIN\login`, DN искать не нужно), контроллер САМ сверяет пароль — `bind` и есть операция
«проверь, что я такой-то», — а той же связью, уже как этот человек, читается его собственная
запись: имя, должность, отдел, группы, фото. На сервере не хранится **ничего**, чем можно
войти в домен: адрес, base DN и шаблон — не секреты (контроллеры видны по DNS SRV любому
сотруднику).

Почему не сервисная учётка: учётка AD, даже бесправная, читает почти весь каталог (все
сотрудники с должностями и почтами, все группы) и входит в любую систему, доверяющую AD; это
долгоживущий пароль на сервере. Search-then-bind сервисной (`bind_dn`/`bind_password`) в коде
оставлен запасным режимом — если домен запрещает сотруднику читать собственные группы; тогда
просить минимальную: только чтение, без интерактивного входа, вход только с хоста сайта.

Грабли, оплаченные живым входом:
- ⚠️ **Пустой пароль отсекается ДО сети:** simple bind с пустым паролем — анонимный bind, и
  каталог отвечает УСПЕХОМ.
- ⚠️ **Таймауты `ldap3` — целые:** `receive_timeout` на Linux пакуется `struct.pack('LL')`, и
  float из конфига ронял открытие сокета на каждом контроллере.
- ⚠️ **TLS к контроллеру:** корень домена обычно не в системном доверии (а CA, положенные
  админами, бывают нечитаемы не-root-процессу) — снять его по AIA промежуточного сертификата
  и указать в `ca_file`; `verify_tls: false` не ставить — пароль ушёл бы тому, кто ответил.
- ⚠️ **Блокировка учётки в домене:** повторные неверные bind'ы блокируют доменную учётку
  целиком, порог обычно 5–10 — `login_limit.attempts` держим ниже; 429 с `Retry-After`.
- Отказы — одним текстом «неверный логин или пароль» (нет такого / неверный / пустой / кривой
  логин): иначе форма — справочник учёток. Каталог недоступен — 503, не 401.
- Логин нормализуется (`CORP\ivanov`, `ivanov@corp` → `ivanov`) и проходит белый список
  `[a-z0-9._-]`; в фильтре поиска экранируется.
- `memberOf` — только прямое членство; вложенная группа маску и `by_group` не пройдёт.
- Пробник — `tools/ldap_probe.py <логин> [--raw]`: тот же код из консоли, печатает DN,
  атрибуты, группы.

## Сессия

Cookie — HMAC-SHA256 из stdlib, внутри только `{sub, prv, iat, exp}`; `HttpOnly`,
`SameSite=Lax`, `Secure` по факту (за прокси — только при `server.trusted_proxy_hops > 0`).
Всё остальное — в **снимке учётки** `data/auth/users/<провайдер>/<логин>.json` (+ `.jpg`):
снимок и есть «сессия существует», **удалил файл — человек разлогинен везде**. Роль считается на
каждый запрос из конфига и снимка: сменил конфиг — роль поменялась без перелогина; правило
доступа ужесточили — чужие сессии кончились на первом запросе. CSRF — `SameSite=Lax` + JSON у
всех изменяющих ручек. Снимки — персональные данные: каталог вне git и вне доставки.

## Роли и права

Кому сайт открыт вообще — `access`: маски групп (`groups`) и логины поимённо (`users`, поверх
масок — для тех, кому сайт нужен без группы); доменный пользователь вне обоих списков получает
403 с `message` (пароль верный — так и говорим), локальные проходят всегда. Правило проверяется
при входе и на каждом запросе: вычеркнули — сессия кончилась.

`viewer < editor < admin`, назначение — `by_user` > `by_group` > роль локального > `default`.
Права — одна таблица `app/auth/roles.py::PERMISSIONS`: `edit` (правка реплик) → editor;
`voices` (имя голоса, «починить везде» — действуют на весь корпус) → admin; `claim` («это я»:
назвать безымянный голос собой, имя из сессии, названный не перебивается) → editor.
`/api/auth/me` отдаёт `can: {edit, voices, claim}` — фронт по ним показывает карандаш и
карточку голоса, рубеж — сервер (`_guard` в `app/api/voices.py`). Правки в словарях подписаны
именем и логином (`_why`), журнал вопросов — полем `user`.

## Маршруты

| | |
|---|---|
| `GET /api/auth/state` | открыто: включён ли вход, провайдеры, название и знак для формы, `home` |
| `POST /api/auth/login` | `{login, password}` → cookie + `me`; 401 / 403 (доступ закрыт) / 429 / 503 |
| `POST /api/auth/logout` | снять cookie |
| `GET /api/auth/me` | логин, имя, роль, должность, отдел, `speaker_name` («Имя Фамилия»), `can`, `home` |
| `GET /api/auth/me/photo` | фото из каталога, если есть |

«Домой» (`home`) — пространство по умолчанию, не корень домена: на общем домене корень может
быть чужим сайтом. Открыты без сессии: `/signin`, `/api/auth/state|login`, `/api/health`,
`/js`, `/css`, `/assets`, `/favicon.svg`, `/sw.js`.
